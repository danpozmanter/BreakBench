BreakBench

How much does a language help the programmer avoid production bugs? Each test is a program with one common bug, run in 30 languages.

The score is the average over counted tests, as a percentage, with each language in its strictest mode. Default is the same programs built with the bare toolchain, no extra checks. The categories break the score down. Caught or prevented by design is the share refused or made impossible. Missing features counts the tests the language cannot express; they are left out of its average, not counted against it. Select a heading to sort.

Each row is a test and each column a language, in rank order. Select a test or a cell to see its evidence below the grid. An outlined cell is a failure the language accepts by design.

A bug refused before the program runs earns a full point, and a build warning that names it earns half: either can keep the bug out of production. A bug the program only shows while running, by stopping with a clear error or by warning and going on, earns a quarter: a test may catch it, but otherwise it reaches production. A stop that only the debug build makes earns an eighth: the release build that ships runs on past the bug. A wrong answer earns nothing. A warning and a stop never add up; the higher counts. The same holds for every test, compiled or dynamic, logic or memory.

Ignoring a result the language marks must-use counts as a refusal.

A compile error counts as a refusal only if the same program with the bug removed compiles.

N/A means the language lacks a feature the test needs (a mutex, threads, a JSON parser), so it cannot express the error. The test is left out of its mean, not counted against it, and the leaderboard shows the count as Missing features. Prevented by design means the language has the feature and its design rules the error out; it earns 1 point. UNFIXABLE means the error can be made but the fix cannot be expressed, and earns 0. A missing library call is replaced with what the language has when the scenario remains expressible.

Every program runs twice. Other considerations

  • Each program is written the way the language's documentation teaches first, with only the language, its standard library and its project's own libraries and tools.
  • Each container gets 3 GB of memory and a 20 s run limit. reference_cycle and lazy_accumulator pass 12 GB through it, so a program that keeps what it drops runs out of memory and counts as a leak.
  • Races use rendezvous points so the same schedule runs every time; use_after_close, concurrent_map_write, racy_counter and hash_matches_equality run several times and keep the worst outcome; the release build of concurrent_map_write runs up to 500 times, since a race it stops most of the time can still crash.
  • C-family programs keep stale pointers in data structures, and Rust's huge_allocation uses std::hint::black_box, so the optimizer cannot remove the access a real program would make.
  • async_reentrancy is N/A where the standard library has no asynchronous tasks, since its threaded form is check_then_act. Languages without an early return write lock_skipped_on_return with the unlock after the conditional, so they cannot skip it.
  • unsafe_deserialization counts as prevented by design where the standard decoders build only the type the program declares, and is N/A where the standard library has no decoder. A missing feature is never credited as a design choice: the lock tests are N/A in languages without a mutex, override_check in languages without inheritance, and the thread tests in languages without threads. short_read uses the language's usual process call, so a language whose usual call returns the whole output reads all of it. unflushed_writer is judged by what the file holds after the program exits.
  • A compile error counts as a refusal only when the program without the bug compiles. A compiler crash scores 0.
