BreakBench

BreakBench

How languages handle bugs. Each test is a program with one bug, run in each language.

Score (with tools)
The share of tests where the language, with the linters, warnings and sanitizers its own project ships, stopped the bug. Every test counts the same.
Coverage
How much of the bench the language can attempt, and in how many of the 13 categories. Tests it lacks a feature for are left out of its scores.
By category
The tests sort into 13 categories (Numbers, Null safety, Concurrency, ...), and some hold far more tests than others. Here each category counts the same: 2 cleanup tests weigh as much as 20 number tests.
By severity
Bugs that let an attacker in or corrupt memory count 3 times, bugs that lose data or stall a service twice, local logic slips once.
Without tools
The compiler and runtime alone.

Where the score comes from

Language constructs: tests whose bug is made with an operator, a cast, a type, a declaration or control flow. Standard-library defaults: tests whose bug is made through a standard-library call, made the way the language teaches first. With safer calls: the score when the program uses the standard library's other call for the same job where one does better (Notes, Safer calls); each such program runs and is scored like the first. The fourth layer, a check the programmer writes by hand, is the fixed program every result is checked against: any language can write it, so it is not scored.

By category

Each cell reads correct / attempted / total. Correct is points: a refusal or correct run earns 1, a run-time stop 0.5 or 0.25. Attempted below total means a missing feature. Caught before running counts refusals and design-prevented tests.

By failure mode

Each test is one program with one input, so one result shows how a language handled that program. A failure mode groups the tests that make the same kind of mistake in different ways (eight integer overflows, eleven missing values); a language that scores well on every test of a mode handles the class, not one instance. Cells read correct / attempted / total.

Each row is a test and each column a language, in rank order. Select a test or a cell to see its evidence below the grid. An outlined cell is a failure the language accepts by design.

Points reflect when the bug is caught and whether it does harm. A refusal stops it before it ships: 1. A clear stop in the shipped build: 0.5. A stop only in the debug build: 0.25. A wrong answer, corruption, crash or hang: 0. A stop counts only if it comes before the result is printed.

The ranked score counts every test once, so a kind of bug with more tests weighs more. Two other weightings sit beside it on the leaderboard. By category gives each of the thirteen categories the same weight, split over the tests it holds. By severity weights each test by how much harm its failure mode does in production, below. A test the language cannot attempt drops out of all three.

A right answer earns its point only where the language defines the behavior that gave it. Where the language leaves that behavior undefined or unspecified, the answer is right by chance and earns nothing: another compiler, allocator or input can change it.

The ranked score counts a finding from the language's own linters and compiler warnings as a refusal (1) and a sanitizer report as a debug-build stop (0.25); the Notes tab says how a finding is tied to the bug. Without tools scores the compiler and runtime alone.

A compile error counts as a refusal only if the same program with the bug removed compiles.

N/A: the language lacks a feature the test needs (a mutex, threads, a JSON parser). The test is left out of its score. Prevented by design: the language has the feature and its design rules the error out; 1 point. Unfixable: the error can be made but not fixed; 0.

What each language lacks, and which tests that rules out. Those tests are left out of its score: no penalty, no credit. The leaderboard's Coverage column shows the share of the bench each language can attempt, so a small feature set shows beside a high score.

How BreakBench builds, runs and scores.

What the score measures

The ranked score measures what a team gets from the language and the tools its own project ships: the compiler or interpreter, the runtime, the switches that make either refuse more or stop more (checked arithmetic, debug builds, assertions, strict typing), and the project's linters, warnings and sanitizers, run the way CI runs them. Without tools leaves those out. Third-party checkers count in neither.

Every test can be passed for full marks by some language design: a compiler that refuses the mistake, or a run that ends correctly because the language made the program handle the failure (a check it requires, a stack that grows). A clean stop at run time earns half.

Tools in the score

Each language's own tooling, run on every program that falls short of full marks. A finding counts when it points at the bug's lines (the same rule as a refusal) and the program without the bug does not get it, so a tool that flags everything earns nothing. A linter or compiler warning earns 1: CI that fails on warnings stops the bug before it ships. A sanitizer report earns 0.25, like a stop only the debug build makes; a report that only restates a crash (a signal) does not count. Every finding is read by hand: one about something other than the bug, such as a style lint on a line the fix rewrites, stays in that result's evidence and does not count.

Checking each result

Every program marks its bug: BREAK! on a line the fix removes, CONTROL! code on a line the fix puts in. Dropping the one and swapping in the other gives the program without the bug.

  • A compile error is a refusal only if the program without the bug compiles and an error points at the bug: a marked line, a line within three of one, the opening line of an enclosing function, match or block, or the declaration of a type a marked line names. Otherwise: Refused Elsewhere, 0.
  • A run that fails the test counts only if the program without the bug, built and run the same way, gives the expected answer; otherwise it is a Benchmark Error. Every such result is checked, except V and Mojo on lost_write_error: neither can detect the failed write (V discards the error; Mojo aborts on an assertion). Tests with no answer of their own give the fixed program one, such as "missing".
  • A build step that runs the program (Clojure) and stops with a run-time error is judged as a run.

Failure modes

Each test covers one mistake, with its CWE, CERT, CVE or pitfall source. Related tests share a failure mode but differ in which check can catch them. missing_argument was removed: it scored like type_confusion in every language.

Tests no language passes

Every language here scores 0 on these. A language could pass each one; none of these does yet.

    Removed tests

    Any test whose result changes between runs, in any language, is removed. Three full runs checked this: all 3,720 results matched, and the two tests changed afterwards matched over five more runs under load. Removed, with the languages that varied (20 runs of one build):

    • concurrent_map_write: unlocked writes to one map. 11 varied: C, C3, C++, Odin (stop or crash); D (hang, wrong answer or stop); Java, Kotlin (hang or wrong answer); Julia (stop or wrong answer); OCaml (stop or hang); F# and Mojo release builds.
    • racy_counter: unlocked increments. C# lost increments in 19 of 20 runs.
    • use_after_close: a write through a freed FILE. C and Nim varied with the allocator's state.
    • hash_matches_equality: equal elements with different hashes. Swift seeds its hash per run: right in 5 of 20.
    • fd_leak: files never closed. Haskell closes handles from a finalizer thread: ran out in 8 of 20.

    check_then_act and async_reentrancy were removed too: a program checks shared state, gives up control (a lock release or an await), then acts on the stale check. Nothing in the program says the two steps belong together, so no compiler or runtime can catch it, and no language could pass.

    Tests that measured a convention rather than a mistake were removed: path_join_escape, split_character, stack_overflow, exit_skips_cleanup, char_arithmetic, huge_allocation, dead_store, unreachable_code and self_deadlock. Each language's behavior there is a legitimate design choice, or the result turned on the input. dead_store and unreachable_code only asked whether a compiler makes a warning an error; self_deadlock gave full marks to re-entrant locks, which many languages leave out on purpose.

    Tests that scored like another test were removed: misspelled_field and newtype passed and failed like type_confusion in every language, strong_enum like newtype in 28 of 30, checked_interpolation like misspelled_field wherever it could be written, and stray_semicolon like dangling_else in 27 of 30. word_and_precedence went too: only Ruby and PHP have the operator, so every other language passed it for free.

    Races stay tested by lock_order_deadlock and lost_wakeup, which force one interleaving. Gap: bugs that show only on some runs (unsynchronized writes, per-run hash seeds) are not measured.

    Right by chance

    A right answer counts only where the language defines the behavior. Where it is undefined or unspecified, the program marks the line and a right answer scores 0 as right by chance.

    • C and C++ evaluation_order: both standards leave the order of a call's arguments unspecified; clang happens to run them left to right.
    • V evaluation_order: V emits one C call holding both arguments, so C's unspecified order applies.
    • C3 container_realloc_dangling: the write through a pointer into the list's old buffer is undefined; the allocator happened to grow the list in place or leave the old buffer unused.
    • Zig, Odin, C3 and Mojo state no order for a call's arguments in their references. Their compilers run them left to right, and they keep the point until a reference says otherwise.

    Every other right answer in C, C++, Zig, Odin, C3, D, Mojo, Nim, V and Goose rests on defined behavior.

    N/A and prevented by design

    N/A only when the language lacks the construct the mistake needs (a mutex, threads, a map literal, inheritance, interpolation). Otherwise the program is written the way the language allows and scored; a design that rules the mistake out runs correctly. A missing feature never counts as prevention.

    The one design marker left is unsafe_deserialization: standard decoders build only the declared type. A language with no standard decoder is N/A there. Kotlin uses kotlinx.coroutines for blocking_in_async.

    One scenario per test

    Each test is one program and one input, written the way the language teaches first. A right answer shows the language handled this program, not every input or idiom. The bench measures classes of mistake through its failure modes instead: each mode holds several tests that make the same kind of mistake in different ways (an overflow in an add, a shift, a subtraction below zero, a parse, a narrow counter), and Details shows each language's result per mode. The safer calls the standard libraries offer are listed below and measured.

    A forced unwrap is counted once, in forced_unwrap. Where the language makes the program check a failure (an Option, a Result, an error union, a checked exception, a call marked try), the other tests handle it there instead of forcing the value out or passing the failure out of main, and the handled program runs correctly. A check the language does not require, such as Go's discarded err, stays out.

    A stop after the answer

    A stop after the result is printed scores as a wrong answer: the wrong value already got out. Examples: Nim empty_max prints 1 before its IndexDefect; unsafe_deserialization, null_byte_path and child_exit_status do harm before any stop.

    Release builds

    What counts as standard

    Allowed: the language and its standard library; libraries the language project itself publishes (Rust regex, Go golang.org/x/text, kotlinx, Haskell aeson); ISO C and POSIX for C and C++; the JVM or .NET class library; every package GHC ships. Not allowed: GNU/BSD extensions, third-party packages, FFI. Each language runs its latest release.

    Other considerations

    • Programs use Option where the standard library returns one, and the default list and integer types. A shared map uses the standard lock-free update where one exists (Clojure atom, Haskell atomicModifyIORef').
    • Each container gets 3 GB of memory and 4,096 processes; each run gets 20 s (reference_cycle, which writes 4 GB, gets 60 s). reference_cycle and lazy_accumulator exceed the cap, so a program that keeps their data runs out of memory: a leak.
    • C-family programs keep stale pointers in data structures, so the optimizer cannot remove the access a real program would make.
    • A compiler crash records ICE and scores 0.
    • Without a sanitizer, C's null dereference and the C-family memory tests run into the hardware or the allocator: a crash, corrupted memory or a wrong answer. C++'s * on an empty std::optional stops through a libstdc++ assertion.
    • A regex engine that gives up at a backtracking limit and reports no match counts as correct. PHP's preg_match returns false, which reads as no match.
    • break_in_switch follows the 1990 AT&T long-distance outage. Where match, when or case does not capture break (Rust, Zig, Kotlin, Python, Ruby, Crystal, Nim, V, Goose, Gossamer), the break leaves the loop and the program runs as written; Scala's boundary wraps the loop. Languages with no switch, or no break, are N/A.
    • json_nan makes its NaN as the mean of zero scores. Python and PHP refuse to divide a float by zero, so they stop at the division before the encoder sees a NaN.
    • forgotten_free allocates the way each language teaches: malloc in C, std::make_unique in C++, an allocator's create or new in Zig, Odin and C3, and an ordinary object or value elsewhere.
    • regex_backtracking stops each run at 10 seconds. Dart's engine gives up backtracking after about 20 seconds on any long input and then answers; a 20-second stall per input is the denial of service the test looks for, and every engine that passes answers in under a second.
    • blocking_in_async uses async/await where the standard libraries can run it, otherwise threads; JavaScript has no blocking sleep, so it runs correctly.
    • OCaml, F#, Haskell and Clojure have no early return, so lock_skipped_on_return unlocks after the conditional and cannot skip it.
    • short_read uses the language's usual process call, so a language whose usual call returns the whole output reads all of it. unflushed_writer is judged by what the file holds after the program exits.
    • The cleanup tests are judged by what the program leaves in /tmp/bb_scratch once it exits. Python, Ruby and Julia create the export file with their standard temporary-file type, which deletes itself; the other languages have none that does.
    • main_error_exit_code is judged by the exit status. main takes the shape the language gives a program that can fail: int main in C, C++ and C3, a Result in Rust and Gossamer, an int entry point in F#, and a main an exception can leave elsewhere.
    • blocked_sender_leak uses each language's standard channel at its default size. Zig and C3 make the program choose a size, so they use an unbuffered one, the most common default. Clojure, JavaScript and TypeScript answer through a promise, Haskell through an MVar.
    • Scala, Clojure, OCaml and F# have no break, so generator_break_cleanup takes the first element (take(1), first, Seq.take 1, Seq.head).
    • timeout_without_cancel uses the language's usual wait with a timeout: Python asyncio.wait_for, Kotlin withTimeoutOrNull, Ruby Timeout.timeout, Haskell timeout and Gossamer sync::with_timeout cancel the work they gave up on; the others only stop waiting.
    • heartbeat_overread follows Heartbleed. A slice that stops at the payload's end (Python, Ruby, JavaScript, PHP, Haskell, Scala, Clojure, F#, Gossamer) returns only what was sent, which is safe. Go reslices up to the buffer's capacity and C copies past the payload, so both send the old message. Java's copyOfRange pads with zeros: no leak, but a wrong reply.
    • deep_json_nesting follows CVE-2020-36518. A parser that sets a depth limit and reports it, or parses the text without the call stack, passes; an exception at run time earns half; a blown stack crashes the process, as one request can in a server.
    • PHP runs 8.5, the newest packaged release. Mojo includes MAX for parallelize.
